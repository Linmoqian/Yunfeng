# pod-agent 文档维护

让指定文档用最少必要内容准确说明当前实现、使用方式和未完成事项。优先删减与修正，维护范围由工程师的任务决定。

## 对照实际，核实时效

先读取根目录 [AGENTS.md](../../../AGENTS.md) 与 [文档维护约定](../../../docs/README.md#文档维护)，检查工作树、暂存区和目标文件差异，保留工程师已有工作。沿目标文档涉及的功能核对源码、配置、命令入口及相关记录，避免把局部维护扩大成全仓库重写。

- 接口名称、字段、目录、版本、命令和已支持能力以当前源码与配置为准。运行结果、设备验收和科研结论必须有对应证据，不能从代码接入推断已经验收。
- 区分当前实现、待实施方案与历史结果。将缺乏依据的完成承诺改为准确状态；暂时无法核实的内容说明具体缺口，不编造日期、结果或能力。
- 修改实现说明时，核对相关 README、专题文档及 `website/content/docs/` 的公开说明，修正同一事实的冲突表述。只更新实际核对过的维护日期与范围，不靠刷新日期制造时效性。
- 历史验收保留原日期、环境和限制，不改写当时结果。仍有独立信息或追溯价值的旧基线按既有 `history/` 规则归档，并移出当前使用入口。

## 文档优先做减法

- 删除重复介绍、空泛背景、无用示例、已失效命令与无独立信息的占位文档。删除或移动文件前核对引用，同步导航和相对链接。
- 同一事实尽量维护在一个权威位置，其他文档用简短摘要和链接引用。工程约束归入 `AGENTS.md`，细节归入对应专题，入口 README 保留使用入口与导航。
- 先给出读者需要的判断或操作，再补充必要条件和限制。短段落表达一个要点；并列内容用短列表，需要比较时再用表格。
- 操作说明保留可执行的命令、运行目录、必要配置和失败后的下一步。压缩措辞时保留数据删除影响、平台限制和科研复核要求，不把关键前提藏掉。
- 不为完整性扩写长篇背景、重复规则或新增多层文档。只在独立模块确实需要使用说明时补充简短 README。

## TODO 只保留当前待办

维护相关文档时同步检查根目录 [TODO.md](../../../TODO.md) 及该功能的待办，结合源码、任务决定与验收记录判断状态。

- 已完成事项及时从活动待办移除；值得保留的交付或验收证据放到对应记录，TODO 不承担完成日志。
- 已取消、被替代或前提已失效的事项，在有证据确认后删除或合并。日期较旧本身不代表过期；尚需真实设备或科研验证的事项不能因代码已写完而删除。
- 部分完成时只留下尚未完成的动作。合并重复事项，每条用一句话写清具体动作和完成条件，必要时附一个详情链接。
- 优先级、负责人、依赖或日期仅在已经明确且有助于推进时保留。避免在 TODO 中堆实施方案、检查流水账、长背景或多层子任务。
- 例如将长篇混合事项收敛为 `- [ ] 在 Android 真机验证报告导出，确认文件可打开。`；已完成的实现与详细验收过程放入对应专题。

## 核对与交付

完成后检查说明是否与实现一致、重复内容是否收敛、活动 TODO 是否仍有实际待办，再在仓库根目录执行 `node scripts/docs/check.mjs` 和 `git diff --check`。

链接检查只覆盖脚本纳入的项目 Markdown/MDX 本地文件目标，不验证字段、站点路由、标题锚点或事实时效；对脚本范围外的文档和这些语义内容另行核对。纯文档维护不新增应用测试或启动生产构建。

按项目 Git 规范仅提交本次差异。交付简短说明删减与同步范围、TODO 清理结果、实际检查结果、无法核实的内容和提交记录。
