2026-10-14，工程师允许评估新的 P2P 协议。先完成 Rust 本地协作存储，再验证认证、配对和网络传输。前端沿用 Yunfeng 的浅白、淡紫、枫叶及圆角 token。个人 Agent 会话沿用现有后端。

本地参考是 `pod-agent/app/desktop/src-tauri` 的 team 服务、领域模型和 `crates/lian-peer-core`，检查时 HEAD 为 `a73bf448`。参考项目已使用 Axum、mDNS、Rustls、Reqwest 等库，不能把它整体视为手写网络实现。其签名事件与密钥身份需要在网络迁移阶段单独验证。

## 分批交付与验收

| 批次 | 实现范围 | 验收条件 |
| --- | --- | --- |
| 一 | Rust 安装档案、SQLite 团队/消息/公告/链接，前端真实 IPC | 数据库重开恢复、幂等性、输入上限、权限与原生保存测试 |
| 二 | 密钥身份、安全保管、限时配对票据、发现与连接 | 两个原生进程双向配对；拒绝过期、重放、错误身份；停止后端口和任务回收 |
| 三 | 团队成员、消息、公告的签名同步 | 两设备离线重连补发，重复事件去重，角色权限和撤销测试 |
| 四 | 文件传输、完整性校验、取消与恢复 | 两设备真实文件校验；路径、大小、并发上限；取消和断线恢复 |

第一批的 installationId 只是安装 UUID，本地 owner 是显示名。后续网络身份必须由密钥认证。第一批本地团队 ID 不代表 LianAgent 签名团队事件，不宣称线协议兼容。未来通过数据库版本迁移绑定公钥与授权信息。

文件页当前只列出所选文件元信息。附近设备与加入按钮标记待接入；这些界面不能作为配对、消息同步或文件传输验收。

## P2P 候选评估

| 候选 | 能力和接入成本 | 需要验证 |
| --- | --- | --- |
| LianAgent Rust HTTPS + mDNS | 可复用现有局域网发现、TLS 和团队业务契约；已有成熟库基础 | 网络权限、证书身份、配对与成员撤销、跨子网可达性 |
| Iroh QUIC | 提供按公钥连接、加密流、穿透和中继；gossip/blobs 可作为后续候选 | 版本与 Rust 工具链兼容、移动平台、依赖体积、无公网环境、连接关闭、团队授权及迁移适配 |

下一批优先做 Iroh 小范围原型，再与参考实现对照。此处是评估方向，尚未添加 Iroh 依赖或更换网络协议。接入前确认握手与版本协商、授权、限时一次性票据和撤销策略。不能用连接加密代替团队成员授权。

Iroh 官方说明提供 QUIC、NAT 穿透与中继退路，不能据此推断所有网络均可直连。中继选择、运营费用、可见元数据及离线可用性需要单独评估；公网中继的启用应作为明确配置。此批没有速度、内存或跨设备基准结果。

来源：[Iroh 官方仓库](https://github.com/n0-computer/iroh)、[mDNS-SD 官方仓库](https://github.com/keepsimple1/mdns-sd)。Context7 CLI 在当前环境不可用，本次查阅官方仓库和本地参考源码。

## 第一批底层选型

SQLite 通过 `rusqlite` 的 bundled 特性接入，锁定解析版本 0.40.2。采用事务、外键、WAL 和持久化安装标识，schema 较新时拒绝打开。新增 `uuid` 的 v4 生成功能和 `url` 标准 URL 解析，`tempfile` 只用于测试。没有新增并发运行时或线程池，使用 Tauri 现有阻塞执行设施，最多接纳一个操作。

`rusqlite` 为 MIT；`uuid`、`url` 为 MIT/Apache-2.0；Iroh 为 MIT/Apache-2.0。实际交付许可证仍以锁定依赖及其源码 LICENSE 为准。SQLite bundled 增加编译工作和二进制内容，但减少对系统 SQLite 版本的依赖；当前没有体积优化测量。网络库接入时须另查维护状态、安全通告、依赖树和许可证。

来源：[rusqlite 官方仓库](https://github.com/rusqlite/rusqlite)、[uuid 官方仓库](https://github.com/uuid-rs/uuid)、[url 官方仓库](https://github.com/servo/rust-url)。

接口、权限、幂等与上限以 [collaboration_action](../api/2026-10-14-collaboration-action.md) 为准。原生功能不提供浏览器假数据回退。

## 当前验证记录与原生验收步骤

2026-10-14 01:25：前端 `pnpm test` 的 32 项测试与 `pnpm build` 通过；构建仍提示部分包超过 500 kB。Rust 格式检查通过，严格 Clippy 通过一轮。随后收紧无字段操作的反序列化契约，Rust 测试及最终检查结果待确认。主机 load average 多次超过 70，原生控制连续超时，开发窗口曾呈现白屏，尚无原生保存成功证据。未创建本批提交。

原生控制不可用时，采用以下手动验收，不以打开页面替代交互验证：

1. 在 `app/desktop/` 运行 `pnpm tauri dev`，等待应用重建完成，打开团队入口。预期显示持久化安装 UUID 和本地保存状态。
2. 创建“测试团队”，显示名使用“测试成员”。预期创建成功后列出本机成员；尚未联网提示可见。
3. 发送“持久化测试消息”，编辑并保存“测试公告”，添加 `https://example.test/` 文档链接。预期 Rust 确认后展示内容；错误输入保留草稿。
4. 关闭本地团队，再从本地列表恢复。预期原消息、公告及链接保留。
5. 正常退出后重新运行开发应用，恢复团队并查看设备档案。预期安装 UUID 和保存内容一致。
6. 浏览器预览中的创建和保存应禁用；配对、附近节点与远端加入应保持待接入状态。

两台设备的网络配对、权限撤销、消息同步和真实文件传输按第二至第四批分别验收。
