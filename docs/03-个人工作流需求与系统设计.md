## 工程师（重新提交）

我来描述我的需求：
1.有记忆能力，会越来越符合我的使用习惯
2.会写TODO
3.git符合我的工作规范

6.辅助我编程

## 助手

工程师，这 7 点已经足以确定产品方向：您需要的不是通用聊天壳，而是一个“个人工作流操作系统”，pi 只负责模型推理、工具循环、会话和上下文压缩。

这些需求可以归并成四个核心系统：

| 系统 | 覆盖需求 |
|---|---|
| 个人记忆 | 使用习惯、纠错、长期偏好 |
| 工程策略 | TODO、Git 规范、编程验证 |
| 上下文引擎 | 自动压缩、项目上下文、任务状态 |
| 可编排工作流 | 联网调研、论文收集阅读、自定义流程 |

## 一、个人记忆不是“保存聊天记录”

建议把记忆分成四类：

```ts
interface PersonalMemory {
  preferences: PreferenceMemory[];
  projectFacts: ProjectMemory[];
  procedures: ProcedureMemory[];
  episodes: EpisodeMemory[];
}
```

### 偏好记忆

记录长期习惯：

```yaml
kind: preference
topic: git
content: 修改后自动提交，但推送必须确认
source: 用户明确指示
confidence: confirmed
scope: global
```

### 项目记忆

记录仅对当前项目有效的事实：

```yaml
kind: project_fact
project: Yunfeng
content: 使用 npm，后端基于 Node.js 和 TypeScript
source: package.json
confidence: observed
```

### 流程记忆

记录“您希望怎么做”：

```yaml
kind: procedure
name: 论文阅读
steps:
  - 检索候选论文
  - 按标题和摘要初筛
  - 等待用户确认
  - 下载全文
  - 转换为 Markdown
  - 提取方法、实验和结论
```

### 情景记忆

记录任务经验：

```yaml
kind: episode
task: 修复会话恢复问题
result: 直接解析 JSONL 容易与 pi 版本不兼容
lesson: 优先使用 SessionManager 公共接口
```

每次任务开始时只检索相关记忆，不能把全部记忆塞进提示词。

```text
当前任务
  → 提取主题、项目和工具
  → 检索相关记忆
  → 注入少量高相关内容
  → 执行任务
  → 产生候选记忆
```

记忆还必须具备：

- 来源；
- 生效范围；
- 置信度；
- 创建时间；
- 最后使用时间；
- 可修改、遗忘和冲突处理；
- 区分“用户明确要求”和“Agent 自己推断”。

## 二、TODO 应该是工具，不只是提示词规则

Agent 不应随意重写 `TODO.md`。应提供专门的 TODO 工具：

```ts
interface TodoTool {
  read(): Promise<TodoDocument>;
  add(item: TodoItem): Promise<void>;
  update(id: string, status: TodoStatus): Promise<void>;
  complete(id: string): Promise<void>;
}
```

任务流程：

```text
接收任务
  → 检查 TODO.md
  → 添加或关联任务
  → 实施过程中更新状态
  → 验证通过
  → 标记完成但不删除
```

TODO 更新应作为任务完成门禁：

```ts
if (task.changedFiles && !task.todoUpdated) {
  return {
    complete: false,
    reason: "代码已修改，但 TODO.md 尚未更新",
  };
}
```

## 三、Git 规范必须代码化

Git 规则分成三层：

### 只读感知

Agent 自动读取：

- 当前分支；
- 工作区状态；
- staged/unstaged 文件；
- diff；
- 最近提交；
- 当前改动是否包含用户原有内容。

### 操作策略

```ts
interface GitPolicy {
  autoCommitAfterChange: true;
  requireApprovalBeforePush: true;
  commitConvention: "conventional-commits";
  commitLanguage: "zh-CN";
  preserveUserChanges: true;
  forbiddenCommands: [
    "git reset --hard",
    "git clean -fd"
  ];
}
```

### 提交门禁

提交前自动检查：

1. 只包含当前任务改动；
2. TODO 已更新；
3. 必要测试通过；
4. 没有凭据和敏感文件；
5. 提交信息符合规范；
6. 不包含 AI 生成相关描述。

例如：

```text
feat(memory): 增加分层记忆存储
fix(session): 修复会话恢复后的事件订阅
docs(todo): 更新编码代理实现进度
```

Git 应当由专门的 `GitService` 操作，不让模型自由拼接任意 Git 命令。

## 四、上下文自动压缩应保留“工作状态”

pi 已有自动压缩能力，但默认摘要不一定符合您的工作流。建议自定义压缩格式：

```md
## 当前目标

## 用户明确要求

## 已确认偏好

## 已完成工作

## 修改的文件

## 关键技术决策

## 测试和验证结果

## 遇到的失败及原因

## 尚未完成

## 下一步
```

压缩时必须保留：

- 用户原始目标；
- 成功标准；
- 明确约束；
- 修改文件和关键代码位置；
- 工具执行结果；
- 失败过的方法；
- 当前 TODO；
- Git 状态；
- 待确认问题。

不应保留：

- 重复讨论；
- 大段终端原始输出；
- 已被后续结论替代的推测；
- 可以重新读取的完整文件内容。

pi 的自定义压缩扩展示例可参考：[custom-compaction.ts](../pi/packages/coding-agent/examples/extensions/custom-compaction.ts)。

## 五、联网能力分成“搜索”和“取证”

联网工具至少要有：

```text
web_search     搜索候选资料
web_open       打开页面
web_download   下载文件
web_extract    转换为可阅读文本
source_store   保存来源及元数据
```

每条网络资料应记录：

```ts
interface SourceRecord {
  url: string;
  title: string;
  author?: string;
  publishedAt?: string;
  accessedAt: string;
  sourceType: "documentation" | "paper" | "article" | "repository";
  localArtifact?: string;
}
```

编程资料应优先：

1. 官方文档；
2. 官方仓库；
3. 标准或论文；
4. 可信技术文章；
5. 论坛和问答作为补充。

这样 Agent 给出的结论能够追溯，而不只是“联网看过”。

## 六、编程能力应该是完整闭环

推荐默认编码工作流：

```text
理解需求
  → 读取项目规则与相关记忆
  → 明确假设和成功标准
  → 检查 TODO 与 Git 状态
  → 定位相关代码
  → 先建立复现或验证方法
  → 最小修改
  → 格式化、静态检查、测试
  → 检查 diff
  → 更新 TODO
  → 提交 Git
  → 总结结果
```

这里 pi 负责：

- 模型推理；
- 文件、Shell、编辑工具；
- 工具循环；
- 会话状态；
- steer/follow-up；
- 自动压缩基础设施。

您的 Runtime 负责控制流程是否真正完成。

## 七、论文流程应当成为可编辑工作流

“论文流程由您来定”意味着不能把流程硬编码进 Agent。可以把它表示成 Markdown/YAML 工作流：

```yaml
name: paper-review
version: 1

inputs:
  - researchQuestion
  - yearRange
  - databases

steps:
  - id: search
    action: searchPapers

  - id: deduplicate
    action: deduplicateByDoi

  - id: screen
    action: summarizeAbstracts

  - id: confirm
    action: askUser
    message: 请确认进入全文阅读的论文

  - id: download
    action: downloadPapers

  - id: convert
    action: convertToMarkdown

  - id: read
    action: structuredReading
    template: templates/paper-reading.md

  - id: synthesize
    action: synthesizeEvidence
```

之后您可以调整：

- 先筛选还是先下载；
- 使用哪些数据库；
- 是否必须确认；
- 阅读提取哪些字段；
- 如何建立引用关系；
- 输出综述、表格还是知识卡片；
- 什么时候写入记忆。

Agent 负责执行流程，不擅自改变流程。

## 建议的总体架构

```text
Web / CLI / Desktop
        │
   自有 Agent API
        │
┌───────┴───────────────────┐
│ Personal Agent Runtime    │
│                          │
│ Memory                    │
│ Workflow                  │
│ Policy                    │
│ Task State                │
│ Source & Artifact Store   │
└───────┬───────────────────┘
        │
    Pi Adapter
        │
┌───────┴───────────────────┐
│ pi-code-agent             │
│ Model / Tool Loop         │
│ Session / Compaction      │
│ Skills / Extensions       │
└───────────────────────────┘
```

第一步需要确定记忆写入策略，因为它会决定整个 Agent 是否可靠：

- **候选记忆 + 自动确认**：Agent 发现习惯后先保存为候选；多次出现或您明确表达后自动转为正式记忆。
- **每次询问确认**：最稳妥，但频繁打断工作。
- **完全自动学习**：最顺滑，但容易把一次性要求误认为长期偏好。

我推荐“候选记忆 + 自动确认”：用户明确说“以后都这样”时立即确认；Agent 推断出的习惯至少重复出现后才生效，并允许您随时查看、纠正和遗忘。工程师是否接受这个记忆策略？
