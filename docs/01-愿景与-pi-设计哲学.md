# 愿景与 pi 设计哲学

## 工程师

我希望做一个自己的通用编码 agent，目前我参考了pi和pi-web这两个仓库，复刻了server-rpc和server两套后端，但是我觉得写的不够好，我希望有自己的思路，让agent适应我的工作流，而不是我适应它，https://pi.dev/ 中为pi的设计哲学

## 助手

工程师，先给结论：您现在写出的主要是两套“pi 的 Web 适配后端”，还不是属于自己的编码 Agent。问题不在代码质量，而在抽象起点仍然是“复刻 pi-web API”。

目前两种实现各有明显边界：

- `server`：直接嵌入 pi SDK，能力完整，但 `routes.ts` 和 `rpc-manager.ts` 都接近 800 行，并开始依赖 pi 的内部状态、扩展运行器和 UI 上下文，升级成本会越来越高。
- `server-rpc`：进程隔离更干净，但仍然复制 pi-web 的接口和 JSONL 读取逻辑，而且通过类型断言调用 `RpcClient` 的私有 `send`，并没有真正稳定的边界。
- 两套后端都以“会话接口有什么”为中心，还没有以“工程师如何完成工作”为中心。
- 当前测试主要验证模块能加载、目录存在，尚未验证真正的 Agent 工作流。
- 项目根目录目前没有 `TODO.md`；开始实施后需要补上并持续维护。

pi 真正值得借鉴的是四条，而不是它现有的接口：

1. 内核只提供稳定原语，不内置具体工作流。
2. 上下文是可设计、可观察的资源。
3. 会话是可分支的事件历史，不只是聊天记录。
4. 工作流通过扩展组合，Agent 可以在运行中被 steer 或追加任务。

这也符合它所说的“Adapt Pi to your workflows, not the other way around”。[pi 设计哲学](https://pi.dev/)

我建议最终形成这样的边界：

```text
您的工作流策略
  ↓
Agent Runtime
  ├─ Turn / Queue / Interrupt
  ├─ Context Builder
  ├─ Tool Runtime
  ├─ Policy / Approval
  ├─ Session Event Store
  └─ Workflow Hooks
  ↓
模型、Shell、Git、文件系统、pi 兼容适配器
```

其中 pi 应当只是一个可替换的执行适配器，而不是系统中心。HTTP、SSE 和未来桌面端也只是 Runtime 的传输层。这样您才能逐步替换 pi，而不用一次重写所有模型、工具和会话能力。

现在第一处必须由您决定的分歧是：

**这个 Agent 的第一目标，是只服务您个人的“有明确偏好、强约束、长期记忆”的编码工作流，还是做成能让不同用户配置自己工作流的通用平台？**

我更推荐先做前者。个人 Agent 可以把 Git 提交、TODO、测试闭环、Windows/conda、权限策略等直接变成一等工作流；通用平台则必须先设计配置系统、租户隔离和扩展协议，复杂度会明显增加。
